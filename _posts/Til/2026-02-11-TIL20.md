# API 설계와 아키텍처 - TIL

## API (Application Programming Interface)

### 정의

서로 다른 애플리케이션끼리 소통하기 위한 설명서(명세서)입니다.

### 사용 시점

- 브라우저 → 백엔드 서버
- 우리 서버 → 다른 서버

**주의**
- 브라우저 → 서버로 직접 요청은 불가능합니다 (CORS 때문에).

---

## 상속 사용 시점

계층형 구조가 필요할 때 상속을 사용합니다.

---

## REST (Representational State Transfer)

### 목적

HTTP의 장점을 살리는 것입니다.
- 무상태성 (Stateless)
- 비연결성 (Connectionless)

### REST의 특징

**1. Client-Server 구조**
- 요청과 응답으로 분리

**2. Cacheable**
- 캐싱 가능

**3. Layered System**
- 계층형 시스템

**4. Uniform Interface (중요)**
- URI와 HTTP Method만 가지고 표현할 수 있습니다.
- 일관성과 확장성을 제공합니다.

### 엔드포인트 설계

**기본 원칙**
- 주소의 마지막 부분이 엔드포인트입니다.
- 예: `/users`

**일관성**
- 회원과 관련된 API는 `/users`로 통일합니다.

### REST API 설계 원칙

**자원은 URI로, 행위는 HTTP Method로 표현합니다.**

```
# 잘못된 설계
POST /createPublicChannel
POST /createPrivateChannel

# 올바른 설계
POST /channels?type=public
POST /channels?type=private
```

**API에 동사를 사용하지 않습니다.**

**쿼리 파라미터**
- 필터링 용도로 사용합니다.
- 예: `?type=public`, `?type=private`

## 웹 API 문서화

### Swagger

웹 API를 문서화할 때 Swagger를 사용합니다.

```java
@RestController
@RequestMapping("/api/users")
@Tag(name = "User", description = "사용자 관리 API")
public class UserController {
    
    @Operation(summary = "사용자 조회", description = "ID로 사용자를 조회합니다")
    @GetMapping("/{id}")
    public ResponseEntity<User> getUser(@PathVariable Long id) {
        return ResponseEntity.ok(userService.findById(id));
    }
}
```

## gRPC

### 정의

### 사용 시점

MSA 환경에서 서비스 간 통신에 주로 사용됩니다.

---

## MSA (Microservices Architecture)

### 정의

여러 개의 독립적인 서비스로 분해하여 운영하는 소프트웨어 구조입니다.

### 특징

- 서버가 서비스별로 나뉘어집니다.
- 각각의 서비스마다 DB를 가질 수 있습니다.

### 장점

- 서비스별로 나누기 때문에 확장에 유리합니다.
- 장애 상황에 유리합니다 (특정 서비스만 영향받음).

### 단점

- 유지하고 구축하는 데 비용이 많이 듭니다.
- 규모가 크지 않은 이상 권장하지 않습니다.

---

## 서버리스 (Serverless)

### 정의

서버가 없는 것처럼 동작합니다 (진짜 없는 것은 아님).
- 직접 서버를 관리하지 않아도 됩니다.
- 필요할 때 작동하고 종료됩니다.

### 비용

서버를 사용하는 만큼만 비용이 발생합니다.

### Java/Spring으로 구현 가능 여부

가능하지만 권장하지 않습니다.
- 효율이 나오지 않습니다.
- 부트스트랩 과정이 오래 걸립니다.

### 장점

- 규모가 작을 때 좋습니다.
- 서버 관리 부담이 없습니다.

### 단점

**1. 실행 시간 제약**
- 하나의 기능이 15분 이상 유지될 수 없습니다.

**2. 모니터링 어려움**
- 디버깅이 어렵습니다.

## API 설계 기본 원칙

### 1. 안정성 (중요)

**필드 순서 유지**
- API 응답의 필드 순서를 일관되게 유지합니다.

```json
// 좋은 예 - 필드 순서 일관성 유지
{
  "id": 1,
  "name": "John",
  "email": "john@example.com",
  "createdAt": "2024-01-01T00:00:00Z"
}
```

### 2. 엔드포인트 설계

**자원은 URI로, 행위는 HTTP Method로 표현합니다.**

| 기능 | HTTP Method | URI | 설명 |
|------|------------|-----|------|
| 목록 조회 | GET | /users | 모든 사용자 조회 |
| 단건 조회 | GET | /users/{id} | 특정 사용자 조회 |
| 생성 | POST | /users | 사용자 생성 |
| 수정 | PATCH | /users/{id} | 사용자 정보 수정 |
| 삭제 | DELETE | /users/{id} | 사용자 삭제 |

### 3. 일관성

- 같은 자원에 대해서는 동일한 엔드포인트를 사용합니다.
- 예: 회원 관련 API는 모두 `/users`로 시작

### 4. 명확성

- URI만 보고도 어떤 자원인지 알 수 있어야 합니다.
- 동사를 사용하지 않고 명사를 사용합니다.

## 아키텍처 비교

| 구분 | Monolithic | MSA | Serverless |
|------|-----------|-----|-----------|
| 구조 | 단일 애플리케이션 | 독립적인 서비스들 | 함수 단위 |
| 확장성 | 낮음 | 높음 | 높음 |
| 관리 복잡도 | 낮음 | 높음 | 낮음 |
| 비용 | 고정 | 높음 | 사용량 기반 |
| 적합한 규모 | 소~중형 | 대형 | 소형 |
| 장애 영향 | 전체 | 부분 | 부분 |

## 핵심 정리

- **API**: 애플리케이션 간 소통을 위한 명세서
- **REST**: URI + HTTP Method로 자원과 행위 표현
- **Uniform Interface**: REST의 핵심 특징
- **엔드포인트**: 동사 사용 금지, 명사로 표현
- **쿼리 파라미터**: 필터링 용도
- **Swagger**: API 문서화 도구
- **gRPC**: 서비스 간 내부 통신
- **MSA**: 대규모 시스템에 적합, 관리 복잡도 높음
- **Serverless**: 소규모에 적합, 15분 제약
- **API 설계 원칙**: 안정성, 일관성, 명확성
