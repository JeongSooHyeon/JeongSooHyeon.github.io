## JPA에서 발생하는 N+1 문제의 발생 원인과 해결 방안

### 발생 원인

#### 1. Eager 전략으로 데이터를 조회하는 경우

```java
@Entity
public class Post {
    @Id
    private Long id;
    
    @ManyToOne(fetch = FetchType.EAGER)  // 즉시 로딩
    private User user;
}

// N+1 발생
List<Post> posts = postRepository.findAll();
// 1. SELECT * FROM post (전체 조회)
// 2. SELECT * FROM user WHERE id = ? (각 post마다 실행)
```

#### 2. Lazy 전략으로 데이터를 가져온 이후 연관 엔티티를 다시 조회하는 경우

```java
@Entity
public class Post {
    @Id
    private Long id;
    
    @ManyToOne(fetch = FetchType.LAZY)  // 지연 로딩
    private User user;
}

// N+1 발생
List<Post> posts = postRepository.findAll();
for (Post post : posts) {
    String userName = post.getUser().getName();  // 각 post마다 user 조회
}
```

---

### 해결 방법

#### 1. Fetch Join

두 테이블을 JOIN하여 한 번에 모든 데이터를 가져옵니다.

```java
@Query("SELECT p FROM Post p JOIN FETCH p.user")
List<Post> findAllWithUser();
```

**장점**
- 한 번의 쿼리로 모든 데이터 조회
- 가장 확실한 해결 방법

**단점**
- 페이징 처리 시 문제 발생 가능
- 카테시안 곱 발생 가능 (일대다 관계에서)

#### 2. @EntityGraph

연관된 엔티티를 명시적으로 즉시 로딩으로 설정합니다.

```java
@EntityGraph(attributePaths = {"user"})
@Query("SELECT p FROM Post p")
List<Post> findAllWithUser();
```

**장점**
- Fetch Join보다 간결한 코드
- 여러 연관 관계 한 번에 지정 가능

**단점**
- Fetch Join과 동일한 한계점

#### 3. Batch Size 설정

```java
@Entity
public class Post {
    @ManyToOne(fetch = FetchType.LAZY)
    @BatchSize(size = 10)
    private User user;
}
```

**장점**
- N+1을 N/batch_size + 1로 줄임
- 페이징 처리 가능

## 트랜잭션의 ACID 속성 중 격리성(Isolation)이 보장되지 않을 때 발생하는 문제점과 해결 방안

### 격리성이 보장되지 않을 때 발생하는 문제점

#### 1. Dirty Reads (더티 리드)

**정의**
- 동시에 진행되고 있는 다른 트랜잭션(아직 커밋하지 않은 상태)에서 변경한 데이터를 현재 진행 중인 트랜잭션에서 읽어 들이는 것

#### 2. Non-Repeatable Reads (반복 불가능한 읽기)

**정의**
- 하나의 트랜잭션 중 읽어 들였던 특정 row의 값을 같은 트랜잭션 내에서 다시 읽어 들이는데, 중간에 변경사항이 생겨(실제로 COMMIT된 변경사항) 결괏값이 다르게 나오는 현상

#### 3. Phantom Reads (팬텀 리드)

**정의**
- 트랜잭션 시작 시점에 데이터를 읽었을 때 존재하지 않았던 데이터가 다시 같은 조건으로 데이터를 읽어 들였을 때 존재해 INCONSISTENT한 결괏값을 반환하는 현상

#### 4. Lost Updates (갱신 손실)

**정의**
- 한 트랜잭션에서 데이터를 변경한 뒤 아직 커밋을 하지 않은 상태에서 읽어 들일 때, 다른 트랜잭션으로 인해 내가 작성한 변경사항이 덮어씌워지는 현상

---

### 트랜잭션 격리 수준 (Isolation Level)

#### 1. READ UNCOMMITTED (레벨 0)

**특징**
- 다른 트랜잭션의 미완료 변경 사항을 읽을 수 있습니다.
- 가장 낮은 격리 수준

---

#### 2. READ COMMITTED (레벨 1)

**특징**
- 다른 트랜잭션이 COMMIT한 데이터만 읽을 수 있습니다.
- **Dirty Read 방지**

---

#### 3. REPEATABLE READ (레벨 2)

**특징**
- 트랜잭션 내에서 같은 데이터를 여러 번 조회해도 값이 변하지 않습니다.
- **Dirty Read, Non-Repeatable Read 방지**

---

#### 4. SERIALIZABLE (레벨 3)

**특징**
- 모든 트랜잭션을 직렬화하여 실행합니다.
- **Dirty Read, Non-Repeatable Read, Phantom Read 방지**
- 가장 높은 격리 수준

**단점**
- 성능 저하 (동시성 최저)
- 데드락 발생 가능성 증가

---

## 핵심 정리

### N+1 문제

**발생 원인**
- Eager 전략 사용
- Lazy 전략 사용 후 연관 엔티티 조회

**해결 방법**
1. Fetch Join (가장 확실)
2. @EntityGraph (간결)
3. Batch Size (페이징 가능)

### 트랜잭션 격리 수준

**문제점**
1. Dirty Reads (커밋 안 된 데이터 읽기)
2. Non-Repeatable Reads (같은 데이터 다른 값)
3. Phantom Reads (유령 데이터 출현)
4. Lost Updates (갱신 손실)

**격리 수준 선택 기준**
- 성능 중요: READ COMMITTED (대부분의 경우)
- 일관성 중요: REPEATABLE READ (MySQL 기본)
- 완벽한 격리 필요: SERIALIZABLE (금융 시스템)
