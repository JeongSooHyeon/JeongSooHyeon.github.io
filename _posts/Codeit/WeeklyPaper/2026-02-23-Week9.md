# 웹 API 발전과 Spring MVC 처리 과정 - TIL

## 웹 API의 발전 과정에서 SOAP에서 REST로의 전환이 일어난 이유와 그 장단점

### SOAP (Simple Object Access Protocol)

#### 정의

XML 기반의 메시징 프로토콜로, 웹 서비스 간 통신을 위해 설계되었습니다.

#### 특징

- 데이터 교환을 위한 규칙과 형식을 정의합니다.
- 주로 엔터프라이즈 환경에서 사용됩니다.
- 보안과 신뢰성이 중요한 시스템에서 활용됩니다.

#### 장점

**1. 표준화된 프로토콜**
- W3C에서 정의한 표준 프로토콜입니다.
- 다양한 플랫폼과 언어에서 호환됩니다.

**2. 높은 보안 수준**
- WS-Security와 같은 보안 기능을 제공합니다.
- 데이터의 무결성과 기밀성을 보장합니다.

**3. 상태 유지**
- 상태를 유지할 수 있는 기능을 제공합니다.
- 복잡한 트랜잭션 처리에 유리합니다.

**4. 트랜잭션 및 메시지 신뢰성 보장**
- 엄격한 표준 기반으로 동작합니다.

#### 단점

**1. 복잡성**
- XML 기반의 메시지 구조로 인해 구현이 복잡합니다.
- 성능이 저하될 수 있습니다.

**2. 무거운 프로토콜**
- HTTP 외에도 SMTP, JMS 등 다양한 프로토콜을 지원합니다.
- 무거운 구조로 인한 과도한 오버헤드가 발생합니다.
- 작은 데이터 전송에도 많은 정보를 포함합니다.

**3. 유연성 부족**
- 개발자에게 높은 진입장벽이 있습니다.
- 표준 문서(WSDL) 학습이 필요합니다.

---

### REST (Representational State Transfer)

#### 정의

HTTP 기반의 아키텍처 스타일입니다.

#### 특징

- 경량화된 데이터 교환을 지원합니다.
- JSON과 같은 다양한 데이터 포맷을 지원합니다.
- 주로 웹 애플리케이션과 모바일 애플리케이션에서 사용됩니다.

#### 장점

**1. 경량 구조**
- HTTP 기반으로 동작합니다.
- JSON, XML 등 다양한 데이터 형식을 지원합니다.
- 데이터 전송이 간편하고 빠릅니다.

**2. 리소스 중심**
- 리소스를 URI로 표현합니다.
- 각 리소스에 대한 CRUD 작업을 쉽게 수행할 수 있습니다.

**3. Stateless (무상태)**
- 클라이언트와 서버 간의 상태를 유지하지 않습니다.
- 서버의 부하를 줄일 수 있습니다.

**4. 명확한 구조**
- 명확한 URI 구조와 HTTP 메서드를 활용합니다.
- 웹 인프라(캐시 등)를 재활용할 수 있습니다.

**5. 다양한 플랫폼 지원**
- 다양한 플랫폼에서 사용 가능합니다.

#### 단점

**1. 보안성 부족**
- 보안 기능이 내장되어 있지 않습니다.
- 추가적인 보안 조치가 필요합니다 (HTTPS, OAuth 등).

**2. 표준화 부족**
- 명확한 표준이 없습니다.
- 구현 방식이 다양해질 수 있습니다.
- SOAP의 WSDL과 같은 엄격한 명세가 없어 문서화가 느슨해질 수 있습니다.

**3. 트랜잭션 관리**
- 트랜잭션, 상태 관리 등은 애플리케이션 레벨에서 처리해야 합니다.

**4. 상태 정보 관리**
- Stateless 특성으로 인해 세션 관리가 어렵습니다.
- 매 요청마다 인증 정보를 전달해야 할 수 있습니다.

---

### SOAP에서 REST로 전환된 이유

#### 1. 성능 향상 및 가벼운 데이터

- SOAP는 장황한 XML을 사용합니다.
- REST는 JSON을 주로 사용하여 페이로드가 작고 통신 속도가 빠릅니다.

#### 2. 높은 유연성 및 캐싱 지원

- HTTP 표준 방식을 그대로 사용하여 캐싱이 용이합니다.
- 다양한 포맷(JSON, XML)을 지원하여 유연합니다.

#### 3. 개발 용이성 및 직관성

- URL과 HTTP 메서드(GET, POST 등)를 활용하여 구조가 직관적입니다.
- 이해하기 쉽고 낮은 학습 곡선을 가집니다.

#### 4. 현대적 환경 적합성

- 모바일, SPA(Single Page Application) 등 현대적인 웹 프레임워크와 친화적입니다.
- 마이크로서비스, 클라우드 환경과 궁합이 좋습니다.

#### 5. 확장성 및 유지보수

- 오픈 API 시대에 적합합니다.
- 확장성과 유지보수가 용이합니다.

---

### SOAP vs REST 비교

| 구분 | SOAP | REST |
|------|------|------|
| 프로토콜 | XML 기반 메시징 프로토콜 | HTTP 기반 아키텍처 스타일 |
| 데이터 형식 | XML | JSON, XML 등 |
| 복잡도 | 높음 (무겁고 복잡) | 낮음 (경량화) |
| 보안 | 내장 (WS-Security) | 별도 구현 필요 (HTTPS, OAuth) |
| 상태 관리 | Stateful (상태 유지 가능) | Stateless (무상태) |
| 트랜잭션 | 내장 지원 | 애플리케이션 레벨 구현 |
| 표준화 | 엄격한 표준 (WSDL) | 느슨한 표준 |
| 학습 곡선 | 높음 | 낮음 |
| 성능 | 낮음 (오버헤드 큼) | 높음 (경량) |
| 캐싱 | 어려움 | 용이함 |
| 사용 환경 | 엔터프라이즈 | 웹, 모바일, 클라우드 |

## Spring Boot에서 @RestController로 들어온 HTTP 요청이 처리되어 응답으로 변환되는 전체 과정

### 전체 처리 흐름

```
1. Client (HTTP 요청)
   ↓
2. DispatcherServlet (Front Controller)
   ↓
3. HandlerMapping (어떤 Controller가 처리할지 결정)
   ↓
4. HandlerAdapter (Controller 메서드 호출)
   ↓
5. @RestController (비즈니스 로직 처리)
   ↓ (객체 반환)
6. HttpMessageConverter (JSON 직렬화)
   ↓
7. DispatcherServlet (응답 전송)
   ↓
8. Client (JSON 응답 수신)
```

---

### 단계별 상세 설명

#### 1. Client의 HTTP 요청

클라이언트가 URI 형식으로 웹 서비스에 요청을 보냅니다.

```
GET /api/users/1 HTTP/1.1
Host: example.com
Accept: application/json
```

#### 2. DispatcherServlet

모든 요청의 진입점(Front Controller)입니다.
- 요청을 처리할 대상을 찾습니다.

#### 3. HandlerMapping

요청 URL과 HTTP 메서드를 기반으로 어떤 Controller의 어떤 메서드가 처리할지 결정합니다.

```java
@RestController
@RequestMapping("/api/users")
public class UserController {
    @GetMapping("/{id}")  // 이 메서드가 선택됨
    public User getUser(@PathVariable Long id) {
        return userService.findById(id);
    }
}
```

#### 4. HandlerAdapter

Controller 메서드를 실행합니다.
- 다양한 타입의 Controller를 지원하기 위해 Adapter 패턴을 사용합니다.
- 메서드 파라미터를 바인딩합니다 (@PathVariable, @RequestParam, @RequestBody 등).

#### 5. @RestController

**비즈니스 로직을 처리하고 객체를 반환합니다.**

```java
@RestController
@RequestMapping("/api/users")
public class UserController {
    
    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        // 비즈니스 로직 처리
        User user = userService.findById(id);
        return user; // 객체 반환
    }
}
```

**@RestController의 특징**
- `@Controller` + `@ResponseBody`와 동일합니다.
- 모든 메서드에 `@ResponseBody`가 자동으로 적용됩니다.
- View를 반환하지 않고 객체를 직접 반환합니다.

#### 6. HttpMessageConverter (핵심)

**동작 시점**
- Controller에서 객체를 반환한 직후
- ViewResolver 대신 동작합니다.

**역할**
1. Java 객체를 HTTP 응답 본문으로 변환합니다 (직렬화).
2. HTTP 요청 본문을 Java 객체로 변환합니다 (역직렬화).

**동작 방식**

```java
// 1. Controller가 객체 반환
User user = new User(1L, "John", "john@example.com");

// 2. HttpMessageConverter가 JSON으로 직렬화
{
  "id": 1,
  "name": "John",
  "email": "john@example.com"
}
```

**주요 Converter**

| Converter | 처리 데이터 | 동작 |
|-----------|------------|------|
| MappingJackson2HttpMessageConverter | JSON | Jackson 라이브러리 사용 |
| StringHttpMessageConverter | String | 문자열 그대로 반환 |
| ByteArrayHttpMessageConverter | byte[] | 바이너리 데이터 처리 |

**Converter 선택 기준**
1. 요청의 `Content-Type` 헤더 확인
2. 응답의 `Accept` 헤더 확인
3. Controller 메서드의 반환 타입 확인

```java
// JSON 요청 → Java 객체 (역직렬화)
@PostMapping("/users")
public User createUser(@RequestBody UserCreateRequest request) {
    // HttpMessageConverter가 JSON → UserCreateRequest 변환
    return userService.create(request);
}

// Java 객체 → JSON 응답 (직렬화)
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    User user = userService.findById(id);
    // HttpMessageConverter가 User → JSON 변환
    return user;
}
```

#### 7. DispatcherServlet

변환된 JSON 데이터를 HTTP 응답으로 전송합니다.

```
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 1,
  "name": "John",
  "email": "john@example.com"
}
```

#### 8. Client

JSON 응답을 수신하고 처리합니다.

---

### @Controller vs @RestController 처리 흐름 비교

#### @Controller

```
Controller → ViewName 반환 → ViewResolver → View → HTML
```

#### @RestController

```
Controller → 객체 반환 → HttpMessageConverter → JSON
```

---

### HttpMessageConverter가 동작하지 않는 경우

**1. @Controller 사용 시**
- ViewResolver가 동작합니다.
- HTML 페이지를 반환합니다.

**2. @ResponseBody 누락 시**
- ViewResolver가 동작합니다.

**해결 방법**
- `@RestController` 사용 또는
- `@Controller` + 각 메서드에 `@ResponseBody` 추가

## 핵심 정리

### SOAP에서 REST로의 전환

**전환 이유**
1. 성능 향상 (JSON vs XML)
2. 개발 용이성 (직관적 구조)
3. 현대적 환경 적합성 (모바일, 클라우드)
4. 캐싱 지원
5. 낮은 학습 곡선

**선택 기준**
- **REST 권장**: 모바일, 웹, 공개 API, 빠른 개발
- **SOAP 권장**: 금융, 엔터프라이즈, 높은 보안 요구

### Spring Boot @RestController 처리 과정

**전체 흐름**
1. DispatcherServlet (요청 수신)
2. HandlerMapping (메서드 선택)
3. HandlerAdapter (메서드 실행)
4. @RestController (객체 반환)
5. **HttpMessageConverter (JSON 직렬화)**
6. Client (JSON 응답)

**HttpMessageConverter**
- **동작 시점**: Controller가 객체를 반환한 직후
- **역할**: Java 객체 ↔ JSON 변환
- **특징**: ViewResolver 대신 동작
