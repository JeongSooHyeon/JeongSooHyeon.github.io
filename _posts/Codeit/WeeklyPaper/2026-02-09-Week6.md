# AOP와 Spring MVC 처리 흐름 - TIL

## AOP가 필요한 이유

### 문제 상황

OOP 방식의 프로그래밍에서 여러 계층에서 공통적으로 사용되는 **공통 관심사**가 중복됩니다.

**예시: 로그인 로직 구현 시**
- 로그인 시도 로그
- 로그인 성공 로그
- 로그인 실패 로그

각 로그인 메서드마다 이러한 로그를 작성하면 중복 코드가 발생합니다.

### AOP를 통한 해결

AOP를 활용하면 공통 관심사를 분리하여 한 곳에서 관리할 수 있습니다.

```java
@Aspect
@Component
public class LoginAspect {
    
    @Before("execution(* com.example.service.LoginService.login(..))")
    public void logBeforeLogin(JoinPoint joinPoint) {
        // 로그인 시도 로그
        log.info("로그인 시도: {}", joinPoint.getArgs());
    }
    
    @AfterReturning(
        pointcut = "execution(* com.example.service.LoginService.login(..))",
        returning = "result"
    )
    public void logAfterLoginSuccess(JoinPoint joinPoint, Object result) {
        // 로그인 성공 로그
        log.info("로그인 성공: {}", result);
    }
    
    @AfterThrowing(
        pointcut = "execution(* com.example.service.LoginService.login(..))",
        throwing = "error"
    )
    public void logAfterLoginFailure(JoinPoint joinPoint, Exception error) {
        // 로그인 실패 로그
        log.error("로그인 실패: {}", error.getMessage());
    }
}
```

### AOP의 장점

1. **비즈니스 로직 단순화**: 핵심 로직에 집중할 수 있습니다.
2. **중앙 집중식 관리**: 공통 기능을 한 곳에서 관리합니다.
3. **코드 가독성 향상**: 핵심 로직과 부가 기능이 분리됩니다.
4. **유지보수성 향상**: 공통 로직 수정 시 한 곳만 변경하면 됩니다.

## Spring MVC 요청 처리 흐름

### @Controller의 처리 흐름

**View를 반환하여 화면을 렌더링합니다.**

```
1. Client
   ↓ (URI 형식으로 요청)
2. DispatcherServlet
   ↓ (요청을 처리할 대상 찾기)
3. HandlerMapping
   ↓
4. HandlerAdapter
   ↓ (요청을 Controller로 위임)
5. Controller
   ↓ (ViewName 반환)
6. DispatcherServlet
   ↓
7. ViewResolver
   ↓ (ViewName에 해당하는 View 찾기)
8. View
   ↓ (HTML 렌더링)
9. Client
```

**특징**
- ViewName을 반환합니다.
- ViewResolver를 통해 실제 View를 찾습니다.
- 화면(HTML)을 렌더링하여 반환합니다.

**코드 예시**

```java
@Controller
@RequestMapping("/users")
public class UserController {
    
    @GetMapping("/list")
    public String getUserList(Model model) {
        List<User> users = userService.findAll();
        model.addAttribute("users", users);
        return "user/list"; // ViewName 반환
    }
}
```

### @RestController의 처리 흐름

**JSON 형태로 객체 데이터를 반환합니다.**

```
1. Client
   ↓ (URI 형식으로 요청)
2. DispatcherServlet
   ↓ (요청을 처리할 대상 찾기)
3. HandlerMapping
   ↓
4. HandlerAdapter
   ↓ (요청을 Controller로 위임)
5. Controller
   ↓ (객체 반환)
6. HttpMessageConverter
   ↓ (JSON으로 직렬화)
7. Client
   ↓ (JSON 데이터 수신)
```

**특징**
- 객체를 반환합니다.
- HttpMessageConverter를 통해 JSON으로 직렬화됩니다.
- `@Controller` + `@ResponseBody`와 동일합니다.
- 모든 메서드가 View 대신 객체로 작성됩니다.

**코드 예시**

```java
@RestController
@RequestMapping("/api/users")
public class UserApiController {
    
    @GetMapping("/list")
    public List<UserDto> getUserList() {
        return userService.findAll(); // 객체 반환 (JSON으로 직렬화됨)
    }
}
```

## @Controller vs @RestController 비교

| 구분 | @Controller | @RestController |
|------|------------|----------------|
| 반환 타입 | ViewName (String) | 객체 (DTO, Entity 등) |
| 사용 목적 | 화면(HTML) 렌더링 | 데이터(JSON) 반환 |
| View 처리 | ViewResolver 사용 | HttpMessageConverter 사용 |
| 응답 형태 | HTML | JSON (또는 XML) |
| 구성 | @Controller | @Controller + @ResponseBody |
| 사용 케이스 | SSR (Server Side Rendering) | CSR (Client Side Rendering), REST API |

## 핵심 정리

### AOP
- **목적**: 공통 관심사 분리
- **효과**: 코드 중복 제거, 유지보수성 향상
- **주요 애노테이션**: @Before, @AfterReturning, @AfterThrowing
- **실제 활용 사례**: 로깅, 보안, 트랜잭션 관리

### Spring MVC
- **@Controller**: View(HTML) 반환, ViewResolver 사용
- **@RestController**: 객체(JSON) 반환, HttpMessageConverter 사용
- **공통점**: DispatcherServlet → HandlerMapping → HandlerAdapter → Controller
- **차이점**: 반환 후 처리 방식 (ViewResolver vs HttpMessageConverter)
