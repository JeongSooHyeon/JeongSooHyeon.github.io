## 애플리케이션의 각 계층에서 수행되는 입력값 검증

### 계층별 검증 책임

#### Controller (프레젠테이션 계층)

**목적**: 요청 데이터의 형식 검증

```java
@PostMapping("/users")
public ResponseEntity<User> createUser(@Valid @RequestBody UserCreateRequest request) {
    // @NotNull, @Email, @Size 등으로 형식 검증
    return ResponseEntity.ok(userService.createUser(request));
}

public record UserCreateRequest(
    @NotNull(message = "이메일은 필수입니다")
    @Email(message = "올바른 이메일 형식이 아닙니다")
    String email,
    
    @NotNull
    @Size(min = 2, max = 50)
    String username
) {}
```

**검증 항목**
- 필수값 여부 (`@NotNull`)
- 길이, 형식 (`@Email`, `@Size`)
- 기본적인 데이터 타입 검증

---

#### Service (비즈니스 계층)

**목적**: 비즈니스 규칙 검증

```java
@Service
@Transactional
public class UserService {
    
    public User createUser(UserCreateRequest request) {
        // 비즈니스 규칙 검증
        if (userRepository.existsByEmail(request.email())) {
            throw new DuplicateEmailException("이미 가입된 이메일입니다");
        }
        
        if (userRepository.existsByUsername(request.username())) {
            throw new DuplicateUsernameException("이미 사용 중인 닉네임입니다");
        }
        
        // 탈퇴한 사용자 재가입 불가
        if (isWithdrawnUser(request.email())) {
            throw new BusinessException("탈퇴한 사용자는 재가입할 수 없습니다");
        }
        
        return userRepository.save(User.of(request));
    }
}
```

**검증 항목**
- 중복 데이터 검사
- 상태 기반 검증
- 비즈니스 규칙 위반 여부

---

#### Domain (도메인 계층)

**목적**: 객체 무결성 보장

```java
public class User {
    private final String email;
    private final String username;
    private final int age;
    
    private User(String email, String username, int age) {
        // 도메인 규칙 검증
        if (age < 0 || age > 150) {
            throw new IllegalArgumentException("올바르지 않은 나이입니다");
        }
        
        this.email = email;
        this.username = username;
        this.age = age;
    }
    
    public static User of(String email, String username, int age) {
        return new User(email, username, age);
    }
}
```

**검증 항목**
- 도메인 불변 조건
- 객체 생성 시 필수 검증
- "항상 유효한 객체" 상태 유지

---

#### Database (데이터 접근 계층)

**목적**: 데이터 무결성 보장

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    email VARCHAR(100) NOT NULL UNIQUE,
    username VARCHAR(50) NOT NULL UNIQUE,
    age INT NOT NULL CHECK (age >= 0)
);
```

**검증 항목**
- `NOT NULL` 제약 조건
- `UNIQUE` 제약 조건
- `FOREIGN KEY` 제약 조건
- `CHECK` 제약 조건

### 중복 검증을 피하면서도 안정성을 확보하는 방안

#### 1. 검증의 "성격"으로 나누기

| 검증 종류 | 담당 계층 | 예시 |
|----------|---------|------|
| 형식 검증 | Controller | @Email, @Size |
| 비즈니스 규칙 | Service | 중복 체크, 상태 검증 |
| 불변 조건 | Domain | 나이 범위, 필수 필드 |
| 데이터 무결성 | Database | UNIQUE, NOT NULL |

**같은 검증을 여러 번 하지 않게 분리**

#### 2. "중복이 아니라 역할 분리"로 보기

**예시: 이메일 검증**
```
Controller: 형식 검사 (@Email)
Service: 중복 검사 (existsByEmail)
Database: UNIQUE 제약 조건
```

겉보기엔 중복 같지만 실제로는 다른 목적의 검증입니다.

#### 3. 공통 검증 로직은 재사용

**Validator 클래스 분리**

```java
@Component
public class UserValidator {
    
    public void validateEmail(String email) {
        if (!email.matches("^[A-Za-z0-9+_.-]+@(.+)$")) {
            throw new InvalidEmailException();
        }
    }
    
    public void validateAge(int age) {
        if (age < 0 || age > 150) {
            throw new InvalidAgeException();
        }
    }
}
```

**도메인 메서드 활용**

```java
public class User {
    private static final int MIN_AGE = 0;
    private static final int MAX_AGE = 150;
    
    public static boolean isValidAge(int age) {
        return age >= MIN_AGE && age <= MAX_AGE;
    }
}
```

### 안정성 확보 전략

#### 핵심 원칙: "방어는 여러 겹으로, 책임은 명확하게"

**Layered Defense (계층형 방어)**

```
Client Request
    ↓
┌─────────────────────────┐
│ Controller              │ → 잘못된 요청 차단
│ (형식 검증)              │
└─────────────────────────┘
    ↓
┌─────────────────────────┐
│ Service                 │ → 비즈니스 보호
│ (비즈니스 규칙 검증)      │
└─────────────────────────┘
    ↓
┌─────────────────────────┐
│ Domain                  │ → 객체 무결성 보장
│ (불변 조건 검증)         │
└─────────────────────────┘
    ↓
┌─────────────────────────┐
│ Database                │ → 최종 안전망
│ (제약 조건)              │
└─────────────────────────┘
```

### 트레이드오프

#### 1. 중복 검증 vs 성능

| 방식 | 장점 | 단점 |
|------|------|------|
| 여러 계층에서 검증 | 안전성 ↑ | 성능 ↓ (미세) |
| 한 곳에서만 검증 | 성능 ↑ | 위험 ↑ |

**현실적인 선택**: 중요한 검증만 중복 허용

#### 2. 책임 분리 vs 코드 복잡도

| 방식 | 장점 | 단점 |
|------|------|------|
| 계층 분리 철저 | 유지보수 ↑ | 초기 개발 난이도 ↑ |
| 단순 구조 | 빠른 개발 | 확장 어려움 |

#### 3. 도메인 검증 강도

| 방식 | 장점 | 단점 |
|------|------|------|
| 강한 도메인 모델 | 안정성 ↑ | 유연성 ↓ |
| 빈약한 도메인 | 빠른 개발 | 버그 위험 ↑ |

#### 4. 사용자 경험 vs 엄격한 검증

| 방식 | 장점 | 단점 |
|------|------|------|
| Controller에서 많이 검증 | UX 좋음 | 코드 복잡 |
| Service/DB에서만 검증 | 단순함 | 에러 늦게 발생 |

---

### 트레이드오프 종합 비교

| 구분 | 장점 | 단점 (Trade-off) |
|------|------|-----------------|
| 철저한 다중 검증 | 보안성 극대화, 어느 계층에서든 데이터 신뢰도 높음 | 코드 중복, 유지보수 포인트 증가, 성능 오버헤드 |
| 도메인 계층 집중 검증 | 로직이 한곳에 모여 유지보수 쉬움, 일관성 높음 | 잘못된 요청이 서비스 레이어까지 침투 (리소스 낭비) |
| 프론트엔드 검증 강화 | UX 개선, 서버 부하 감소 | 보안 대책 불가 (API 직접 호출 시 무력화) |

## 테스트에서 사용되는 Mockito의 Mock, Stub, Spy 개념

### Mock (행위 검증)

#### 정의

호출 여부를 검증하기 위한 객체입니다. 실제 로직은 없고 모든 동작이 가짜입니다.

#### 사용 시점

- 외부 의존성(DB, API 등)을 끊고 싶을 때
- 행위 검증이 필요할 때

#### 주요 메서드

- `when()`: 특정 메서드 호출 시 반환값 지정
- `verify()`: 메서드가 호출되었는지 확인

#### 예시: 회원 가입 테스트

```java
@Test
void 회원가입시_저장이_호출되는지_검증() {
    // given
    UserRepository mockRepository = mock(UserRepository.class);
    UserService userService = new UserService(mockRepository);
    
    User user = new User("test@example.com", "testuser");
    
    // when
    userService.createUser(user);
    
    // then
    verify(mockRepository).save(user);  // save() 호출 여부 확인
    verify(mockRepository, times(1)).save(any());  // 1번 호출되었는지 확인
}
```

**핵심 질문**: "이 메서드가 호출되었는가? 몇 번 호출되었는가?"

### Stub (상태 검증)

#### 정의

미리 정해진 값을 반환하도록 만든 객체입니다. 테스트를 위해 입력과 출력만 맞춥니다.

#### 사용 시점

- 서비스 로직 결과를 검증할 때
- 외부 의존성의 반환값만 필요할 때

#### 주요 메서드

- `when().thenReturn()`: 특정 입력에 대한 반환값 지정

#### 예시: 중복 이메일 검증 테스트

```java
@Test
void 이메일_중복시_예외_발생() {
    // given
    UserRepository stubRepository = mock(UserRepository.class);
    UserService userService = new UserService(stubRepository);
    
    String email = "duplicate@example.com";
    when(stubRepository.existsByEmail(email)).thenReturn(true);  // Stub 설정
    
    // when & then
    assertThrows(DuplicateEmailException.class, 
        () -> userService.createUser(email));
}
```

**핵심 질문**: "이 입력에 대해 이 결과가 나오는가?"

---

### Spy (부분 Mock)

#### 정의

실제 객체를 감싸면서 일부만 가짜로 바꾸는 객체입니다. 실제 로직 + 부분 Mock입니다.

#### 사용 시점

- 실제 동작을 유지하면서 일부만 제어하고 싶을 때
- 기존 로직을 대부분 유지하고 싶을 때
- 일부 메서드만 오버라이드하고 싶을 때

#### 특징

- 진짜 메서드가 실행됩니다.
- 특정 메서드만 stub 가능합니다.

#### 예시: 이메일 검증 로직 부분 테스트

```java
@Test
void 이메일_검증_로직만_변경해서_테스트() {
    // given
    UserRepository repository = mock(UserRepository.class);
    UserService spyService = spy(new UserService(repository));
    
    // 실제 isValidEmail()은 복잡한 로직이지만, 테스트에서는 항상 true 반환
    doReturn(true).when(spyService).isValidEmail(any());
    
    // when
    spyService.createUser("invalid@email");  // 나머지 로직은 실제로 실행됨
    
    // then
    verify(repository).save(any());  // 실제 save 로직까지 실행됨
}
```

### 실전 예시 비교

#### 회원 가입 테스트

**Mock 사용 (행위 검증)**

```java
@Test
void Mock_저장_호출_여부_검증() {
    // given
    UserRepository mockRepository = mock(UserRepository.class);
    UserService service = new UserService(mockRepository);
    
    // when
    service.createUser(user);
    
    // then
    verify(mockRepository).save(user);  // 호출 여부 확인
}
```

**Stub 사용 (결과 검증)**

```java
@Test
void Stub_중복_이메일_예외_검증() {
    // given
    UserRepository stubRepository = mock(UserRepository.class);
    when(stubRepository.existsByEmail(email)).thenReturn(true);  // 반환값 설정
    
    UserService service = new UserService(stubRepository);
    
    // when & then
    assertThrows(DuplicateEmailException.class,
        () -> service.createUser(email));  // 결과 확인
}
```

**Spy 사용 (부분 테스트)**

```java
@Test
void Spy_일부_로직만_변경() {
    // given
    UserRepository repository = mock(UserRepository.class);
    UserService spyService = spy(new UserService(repository));
    
    doReturn(true).when(spyService).isValidEmail(any());  // 일부만 강제 변경
    
    // when
    spyService.createUser("invalid");  // 나머지는 실제 로직 실행
    
    // then
    verify(repository).save(any());
}
```

### Mock, Stub, Spy 선택 가이드

| 상황 | 사용 | 이유 |
|------|------|------|
| 메서드 호출 여부 확인 | Mock | 행위 검증 |
| 외부 API 응답값 필요 | Stub | 상태 검증 |
| 대부분 실제 로직 유지 | Spy | 부분 Mock |
| DB 없이 테스트 | Mock/Stub | 의존성 제거 |
| 복잡한 로직 일부만 변경 | Spy | 실제 로직 활용 |

## 핵심 정리

### 입력값 검증 전략

**계층별 책임**
- Controller: 형식 검증 (@Valid, @Email, @Size)
- Service: 비즈니스 규칙 (중복 체크, 상태 검증)
- Domain: 객체 무결성 ("항상 유효한 객체")
- Database: 데이터 무결성 (UNIQUE, NOT NULL)

**안정성 확보**
- Layered Defense (계층형 방어)
- Fail-Fast 전략
- 도메인 모델 중심 검증

**트레이드오프**
- 중복 검증 ↔ 성능
- 책임 분리 ↔ 복잡도
- 강한 도메인 ↔ 유연성

### Mockito

**Mock**: 행위 검증 (verify)
**Stub**: 상태 검증 (when().thenReturn())
**Spy**: 부분 Mock (실제 로직 + 일부 변경)
