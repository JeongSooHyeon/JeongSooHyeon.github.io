# SQL DDL/DML과 역정규화 - TIL

## SQL에서 DDL과 DML의 차이점

### DDL (Data Definition Language)

#### 정의

데이터 정의 언어로, 데이터베이스의 구조를 정의하고 관리합니다.

**대상 객체**
- 테이블
- 뷰
- 인덱스
- 프로시저

#### 주요 명령어

**CREATE**
- 테이블, 뷰, 인덱스와 같은 새 데이터베이스 객체를 생성합니다.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50),
    email VARCHAR(100)
);
```

**ALTER**
- 기존 데이터베이스 객체를 수정합니다.

```sql
ALTER TABLE users 
ADD COLUMN age INT;
```

**DROP**
- 기존 데이터베이스 객체를 삭제합니다.

```sql
DROP TABLE users;
```

**TRUNCATE**
- 테이블의 모든 행을 삭제합니다.
- DROP과 달리 테이블의 구조와 인덱스는 그대로 유지됩니다.

```sql
TRUNCATE TABLE users;
```

---

### DML (Data Manipulation Language)

#### 정의

데이터 조작 언어로, 데이터베이스 내의 데이터를 조작합니다.

**주요 작업**
- 삽입 (Insert)
- 조회 (Select)
- 수정 (Update)
- 삭제 (Delete)

#### 주요 명령어

**SELECT**
- 테이블에서 데이터를 검색합니다.

```sql
SELECT * FROM users 
WHERE age > 20;
```

**INSERT**
- 테이블에 새로운 데이터를 삽입합니다.

```sql
INSERT INTO users (username, email, age) 
VALUES ('john', 'john@example.com', 25);
```

**UPDATE**
- 테이블의 기존 데이터를 수정합니다.

```sql
UPDATE users 
SET age = 26 
WHERE username = 'john';
```

**DELETE**
- 테이블에서 데이터를 삭제합니다.

```sql
DELETE FROM users 
WHERE age < 18;
```

---

### DDL vs DML 비교

| 구분 | DDL | DML |
|------|-----|-----|
| 목적 | 데이터베이스 구조 정의 | 데이터 조작 |
| 대상 | 스키마, 테이블, 인덱스 등 | 테이블 내의 데이터 |
| 롤백 | 롤백 불가 (Auto Commit) | 롤백 가능 (트랜잭션) |
| 주요 명령어 | CREATE, ALTER, DROP, TRUNCATE | SELECT, INSERT, UPDATE, DELETE |
| 실행 빈도 | 낮음 (초기 설계 시) | 높음 (일상적 작업) |

## 역정규화가 필요한 상황과 적용 시 고려사항 및 장단점

### 역정규화가 필요한 상황

#### 1. 복잡한 JOIN으로 인한 성능 저하

여러 테이블을 JOIN해야 하는 쿼리가 자주 실행되어 성능이 저하될 때

```sql
-- 정규화된 구조 (느림)
SELECT u.name, o.order_date, p.product_name
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id;
```

#### 2. 조회 빈도가 높은 컬럼들을 빠르게 접근하고 싶을 때

자주 조회되는 데이터를 한 테이블에 모아두면 성능이 향상됩니다.

#### 3. 정규화로 인해 지나치게 많은 테이블이 생성된 경우

과도한 정규화로 테이블이 너무 많아져 관리가 어려울 때

#### 4. 조회 작업이 입력/갱신 작업보다 훨씬 많은 경우

읽기 작업이 대부분인 시스템(리포트, 분석 시스템 등)

---

### 적용 시 고려해야 할 사항

#### 1. 데이터 중복

**문제점**
- 중복된 데이터로 인해 저장 공간이 늘어납니다.
- 변경 시 여러 곳을 수정해야 합니다.

**고려사항**
- 중복으로 인한 저장 공간 증가량 계산
- 수정 작업의 복잡도 평가

#### 2. 데이터 무결성 유지 방법

**문제점**
- 중복 필드가 수정되었을 때 전체 일관성 유지가 어렵습니다.

**고려사항**
- 트리거나 애플리케이션 로직으로 일관성 보장 방법 설계
- 동기화 메커니즘 구현

#### 3. 성능 개선의 실제 효과 측정

**고려사항**
- 역정규화가 진짜 필요한지 검증
- 쿼리 속도 차이를 실제로 측정
- 부하 테스트를 통한 검증

#### 4. 트랜잭션 복잡성 증가 가능성

**문제점**
- 데이터를 여러 테이블에 동시에 수정해야 할 수 있습니다.

**고려사항**
- 트랜잭션 범위 확대로 인한 성능 영향 평가
- 데드락 가능성 검토

---

### 역정규화의 장단점

#### 장점

**1. 조회 성능 향상**
- JOIN이 줄어들어 쿼리 실행 속도가 빨라집니다.
- 필요한 데이터가 하나의 테이블에 있어 빠르게 조회 가능합니다.

```sql
-- 역정규화 후 (빠름)
SELECT name, order_date, product_name
FROM denormalized_orders;
```

**2. 리포트용 쿼리 간소화**
- 복잡한 쿼리 없이도 데이터를 쉽게 가져올 수 있습니다.
- 리포트 작성이 쉬워집니다.

**3. 응답 속도 개선**
- 실시간 성능이 중요한 시스템에 유리합니다.
- 사용자 경험 향상에 기여합니다.

#### 단점

**1. 데이터 중복**
- 중복 필드가 많아질수록 관리가 어려워집니다.
- 저장 공간이 낭비됩니다.

**2. 데이터 무결성 유지 어려움**
- 하나의 값 변경이 여러 테이블에 반영되어야 합니다.
- 실수 가능성이 높아집니다.
- 데이터 불일치 위험이 증가합니다.

**3. 쓰기/수정 성능 저하 가능성**
- 데이터를 갱신할 때 처리 범위가 넓어집니다.
- 트랜잭션이 복잡해집니다.
- 동시성 제어가 어려워질 수 있습니다.

---

### 역정규화 적용 예시

#### 정규화된 구조

```sql
-- users 테이블
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50)
);

-- orders 테이블
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,
    order_date DATE,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

#### 역정규화된 구조

```sql
-- 역정규화: username을 orders 테이블에 포함
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,
    username VARCHAR(50),  -- 중복 데이터
    order_date DATE
);
```

**장점**: 주문 조회 시 JOIN 불필요
**단점**: username 변경 시 orders 테이블도 함께 업데이트 필요

## 핵심 정리

### DDL vs DML

**DDL (Data Definition Language)**
- 구조를 정의: CREATE, ALTER, DROP, TRUNCATE
- 롤백 불가 (Auto Commit)

**DML (Data Manipulation Language)**
- 데이터를 조작: SELECT, INSERT, UPDATE, DELETE
- 롤백 가능 (트랜잭션)

### 역정규화

**적용 상황**
- 복잡한 JOIN으로 성능 저하
- 조회 빈도가 높은 시스템
- 읽기 작업이 대부분인 경우

**장점**
- 조회 성능 향상
- 쿼리 간소화
- 응답 속도 개선

**단점**
- 데이터 중복
- 무결성 유지 어려움
- 쓰기/수정 성능 저하

**결론**: 역정규화는 조회 성능이 중요하고 쓰기 작업이 적을 때 신중하게 적용해야 합니다.
